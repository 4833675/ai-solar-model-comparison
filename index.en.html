Before We Begin

What This Comparison Does—and Does Not—Demonstrate

What it demonstrates: the quality of a brief directly affects the quality of the result. The same model can produce work on an entirely different level when given a full specification instead of one sentence.

Vague requirements: some highly capable models can still do excellent work from a vague request because of their own strengths. Less capable models tend to need a detailed description of the process, steps, and other implementation guidance.

Why some models were rerun: some models were run many times because their early results differed sharply from expectations, promotional claims, or the performance shown in other evaluations. Repeated runs nevertheless produced essentially the same outcome.

PS: this test covers only coding ability and the ability to interpret vague requirements. Other capabilities, such as Chinese-language writing, are outside its scope.

COUNTERINTUITIVE FINDING · COST TO OUTCOME

A lower price does not mean cheaper completion

Once you have a detailed specification, should you automatically switch to a cheaper, less capable model? Quite the opposite: a specification can reduce ambiguity, but it cannot erase a capability gap. Add quota consumption, waiting, failures, rework, and human review, and the lower-priced model may cost more to finish the same project.

A specification amplifies capability.
It does not replace it. The useful metric is cost per accepted result.
Keep the units straight

In the Claude cases, a “five-hour allowance” means usage within one quota window; it does not mean five hours of continuous runtime. 17:40 and 35:24 are measured wall-clock durations. The comparisons below stay within like-for-like units; the two kinds of measurement are not converted into each other.

COMPLETE SAMPLE SUMMARIES

Expand the complete Claude Opus 5 (Max) sample summaryRechecked against the V2 Evidence Score and same-model pairs

I broadly agree with GPT-5.6 Sol (Max)'s risk-routing framework, but these samples show something else: prompt format materially changes coverage scores, so a cross-group total should not be read directly as model capability.

A specification raises the floor of requirement coverage; it does not automatically raise the ceiling of execution quality.

1. What the same-model pairs show

Across the 23 same-model pairs, the coverage component of the V2 Evidence Score rises from 41.86 / 59.5 for the one-line group to 55.95 / 59.5 for the detailed-spec group. The specification clearly makes requested items more likely to appear in the result. Claude Opus 4.8 is a (Max → Ultra) reasoning-level exception, so these pairs are not one uniformly controlled experiment.

Execution quality—correctness and stability, visual execution, and interaction completeness—is 30.32 / 40.5 versus 31.41 / 40.5, with no stable lift. This sample supports “the specification improves requested-feature coverage.” It is insufficient to conclude that specifications reduce execution quality overall, and it is insufficient for any general model ranking.

Prompt format therefore remains an important confounder in cross-group totals. To discuss the effect of the specification, prefer the 23 paired results over treating all 40 one-line and 34 detailed-spec works as equivalent samples.

2. What a specification does—and does not do

A specification can reduce failures of omission. Orbital elements, eight moons, Halley, offline operation, and the rendering pipeline are written down, so models are more likely to attempt them.

It does not automatically remove failures of execution. The detailed-spec group still contains mixed coordinate spaces in ring shadows, a wrong Venus semimajor axis, a Saturn ring scaled into practical invisibility, a Great Red Spot that never rotates into view, NaN in live solar data, and render loops that multiply in the background. These often produce no explicit error; someone has to open the work, observe it over time, and return to the source.

A specification reduces ambiguity at the input; it does not perform acceptance at the output.

The V2 rubric therefore separates source presence into traceable feature, orbit-model, runtime-consistency, and interaction evidence, with fatal caps for severe failures. The formula is automatic; evidence collection is not fully automatic. Visual and some interaction judgments still include human review.

3. What this means for cost

This sample does not use one uniform billing method, and it lacks controlled data that strictly pairs model-call price with accepted outcomes. It therefore cannot establish which tier is generally the cheapest.

A cheaper call does not guarantee a cheaper accepted result.

The relevant quantity is the total cost of one accepted result: model calls, specification work, waiting, failed attempts, bug fixing, human supervision, and final review. The more silent the failure, the more expensive it is to discover. Stepping down is evidence-based only when a lower tier reliably passes the same acceptance suite on comparable work and truly lowers total cost.

4. Reruns and evidence boundaries

Some models were rerun because early results differed sharply from expectations, marketing claims, or other evaluations. Follow-up runs did not change the overall impression. But the reruns were unplanned and unequal, and the currently visible repeats mix prompt formats, versions, or environments. They cannot estimate a common variance across models or form a fair ranking.

The sample has four further boundaries:

  • It tests one open-ended 3D coding task, not writing, translation, extraction, or most engineering work.
  • Platforms, agent environments, caches, and accounting methods were not identical; this is not a controlled laboratory experiment, and the Claude Opus 4.8 pair changes from (Max) to (Ultra).
  • Claude Opus 5 (Ultra) authored the specification and later answered it, giving that run a “write the exam, then take it” advantage.
  • Visual and some interaction evidence remains human-reviewed. The V2 Evidence Score improves transparency; it does not eliminate judgment error.

These samples therefore support the claim that a detailed specification improves requested-feature coverage. They are insufficient to establish a general model ranking or conclude that specifications reduce execution quality.

5. Four operational judgments

  • Default to the strongest model, with explicit step-down triggers. Not because the strongest is always optimal, but to avoid rebuilding a routing table that depreciates quickly.
  • Use failure visibility before stepping down. Compiler errors, failed tests, and empty results surface immediately. Silent orbit, visual, and long-run failures require human discovery cost.
  • Write acceptance before choosing a model. Without executable checks, a multi-model trial can collapse into surface impressions.
  • Use advisors only where sticking points are recognizable. An executor will not ask for help with an error it does not know it made.

In one sentence:

Do not save tokens by buying a failure that a person must discover.

After weighing it again, I would revise my previous conclusion: these samples support prioritizing the strongest suitable model for complex, ambiguous work where rework is expensive, but they do not justify using the strongest model by default for every task.

Default to neither the strongest nor the cheapest model. Route by risk first, then by measured results.

The real quantity to optimize is:

The expected total cost of producing one result that passes acceptance.

That includes more than the model bill: model calls and token consumption, specification preparation, human supervision, final review, failed attempts, bug fixing, waiting, and delay.

Across the 23 same-model pairs, the V2 Evidence Score shows coverage rising from 41.86 / 59.5 to 55.95 / 59.5, while execution quality is 30.32 / 40.5 versus 31.41 / 40.5. This supports the conclusion that a detailed specification improves requested-feature coverage, but it shows no stable lift in execution quality. A specification can amplify capability; it cannot replace interpretation, planning, self-review, correction, or acceptance.

A more defensible strategy is:

  • Unknown, complex, open-ended, or expensive to fail: prioritize the strongest suitable model and avoid turning the price gap into rework.
  • Clear, low-risk, machine-testable, and high-volume: use the lowest-cost model that has demonstrated reliable acceptance on comparable tasks.
  • Long workflows with mostly mechanical steps: test a smaller executor with a frontier advisor, but compare it with frontier-model solo performance; results are task-dependent and should be measured on the actual workload.
  • No reliable data yet: establish a quality baseline, acceptance criteria, and a test set before deciding whether to step down.

These judgments have clear boundaries. Some models were rerun because early results conflicted with expectations, marketing claims, or other evaluations. Follow-ups did not change the overall impression, but the reruns were unequal and unplanned, so they cannot estimate a common variance or form a fair ranking.

In one sentence:

The default is not “always use the strongest.” It is risk-based routing: use the strongest under high uncertainty and a demonstrated, sufficiently capable model under low uncertainty.

Key Terms

These terms describe how a model reasons, uses tools, and organizes work; they are not a capability ranking. Product names differ across platforms, so the definitions below explain how this site uses them.

ADVISOR STRATEGY

Advisor strategy

A faster, lower-cost executor model advances the task end to end. When it reaches a pivotal decision it cannot reasonably resolve, it shares the context with a stronger advisor model. The advisor returns a plan, correction, or stop signal, and the executor resumes.

Executor advances→Consult a stronger model at a pivotal decision→Executor resumes and delivers

This is not sub-agent orchestration: the advisor does not call tools, produce the final result, decompose the job, or launch a worker pool. It only guides the executor.

ULTRA REASONING

Ultra reasoning tier

On this site, Ultra means the highest or strongest agentic-reasoning tier that the test platform offers for a model. It is not a cross-vendor standard or necessarily part of the official model name; comparable settings may be called Max, xHigh, high, or thinking elsewhere.

What it implies: the main agent generally receives a larger reasoning and work budget for planning, retrieval, self-review, and validation. It may also take longer and consume more quota. Ultra still does not mean “guaranteed correct.”

Recommendation in this site's context: in an environment that supports sub-agents, run the main agent at Ultra and let it decide whether to decompose the task, assign suitable sub-agents, and own final integration and acceptance.

RECOMMENDED ORCHESTRATION

How an Ultra main agent organizes sub-agents

The main agent retains the objective, context, and final responsibility. A sub-agent receives only a bounded piece of work that can be completed independently.

Main agent · UltraUnderstand the objective and acceptance criteria→ Decide whether to splitIdentify independent or parallel subtasks→ Assign sub-agentsChoose workers by specialty, speed, and cost→ Integrate and acceptReview results, run tests, and deliver one whole

Different from the advisor strategy: a sub-agent performs a real subtask and returns a result. An advisor only gives guidance while the original executor remains in control of the main workflow.

AGENT

Agent

The primary actor that can read context, call tools, edit files, run checks, and keep advancing toward an objective—not merely a chat model answering one turn.

SUB-AGENT

sub-agent

A child worker assigned a specific, bounded task by the main agent. It can investigate or implement in parallel, but the main agent should still integrate and verify its result.

REASONING TIER

Reasoning tier

A setting for the thinking and work budget available to the same model. Higher tiers usually plan and check more thoroughly, but may run longer and consume more quota.

COST TO ACCEPTANCE

Total acceptance cost

Everything required to obtain one acceptable result: model usage, waiting, failed attempts, bug fixing, human supervision, and final review—not just token price.

SCORE ≠ TIER

Evidence Score vs. subjective tier

Evidence values come from source audit, consistent runtime review, and human visual review; formula and sorting are automatic. Tiers are the site author's subjective grouping of practical completeness.
