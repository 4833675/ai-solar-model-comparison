Before We Begin

What This Comparison Does—and Does Not—Demonstrate

What it demonstrates: the quality of a brief directly affects the quality of the result. The same model can produce work on an entirely different level when given a full specification instead of one sentence.

Vague requirements: some highly capable models can still do excellent work from a vague request because of their own strengths. Less capable models tend to need a detailed description of the process, steps, and other implementation guidance.

What it cannot demonstrate: an overall ranking of model capability. The Design Specification was produced by Claude Opus 5 by reverse-engineering its own implementation, and Section 7 explicitly lists all fifteen implementation traps. The specification group was therefore given both a set assignment and a strategy guide: they were solving a problem whose answer was already known. It would be invalid to use that alone to rank the models.

Also: Claude Opus 5 and Fable 5 Max have no specification-based versions—the specification came from the former—so they are not included in the same-model comparison. Some other models appear in only one group, and the site presents them separately as such.

Reasoning levels were aligned: every entry in both groups was produced at that model's highest available reasoning level. Suffixes such as Max, xHigh, Ultra, and high are different vendors' names for their highest settings. For example, GPT-5.5 offers xHigh, while DeepSeek uses high and max as compatible names for the same level. The only variable between the two groups is the form of the requirement; neither group received more reasoning compute. For a cleaner display, parenthetical level markers such as high and thinking have been omitted from model names.

PS: this test covers only coding ability and the ability to interpret vague requirements. Other capabilities, such as Chinese-language writing, are outside its scope.

COUNTERINTUITIVE FINDING · COST TO OUTCOME

A lower price does not mean cheaper completion

Once you have a detailed specification, should you automatically switch to a cheaper, less capable model? Quite the opposite: a specification can reduce ambiguity, but it cannot erase a capability gap. Add quota consumption, waiting, failures, rework, and human review, and the lower-priced model may cost more to finish the same project.

A specification amplifies capability.
It does not replace it. The useful metric is cost per accepted result.
Keep the units straight

In the Claude cases, a “five-hour allowance” means usage within one quota window; it does not mean five hours of continuous runtime. 17:40 and 35:24 are measured wall-clock durations. The comparisons below stay within like-for-like units; the two kinds of measurement are not converted into each other.

Total project cost=model usage+spec preparation+failed attempts+bug fixing / rework+human review+waiting & delay

Practical conclusion: first choose a model capable of getting the task right, then use a specification to amplify its reliability and control. For complex, high-risk work where rework is expensive, one successful premium call may cost less than several cheaper attempts.

Evidence boundary: these are records from real projects, not a standardized benchmark. Sol Ultra is currently the only top-tier model tested with the detailed specification. Giving the same spec to other frontier models would likely widen the gap, but that is an inference from the present samples—not a result verified model by model.

How Do You Choose a Model—and Get Better Results from It?

Start with ambiguity, failure risk, and the cost of rework. Do not choose from a leaderboard alone.

Use a frontier model directly

Ambiguous, high-risk, expensive to redo

For an unfamiliar codebase, architecture work, difficult debugging, or production changes, start with the strongest model available. Have it investigate the context and propose a plan and acceptance criteria before it edits anything.

Advisor + executor

A long workflow with mostly mechanical steps

Let a faster, more economical model read files, edit code, and run tests. Give plan selection, persistent blockers, and final review to a stronger model.

Execute directly

Clear, low-risk, and quick to verify

For routine edits, formatting, and batch work, a faster model can execute directly. A clear objective, constraints, and acceptance criteria are usually more useful than a long prescription of every step.

Run a real pilot first

You do not know which model fits

Give several models the same representative tasks, then compare success rate, rework, time, and cost. Do not choose a long-term default from one dazzling answer.

ADVISOR STRATEGY

Let the strongest model make pivotal decisions, and an executor model carry the workflow through

Original article ↗ Official documentation ↗

Anthropic's Advisor Strategy does not ask the strongest model to do everything from start to finish. A faster, more economical executor model advances the task end to end. When it reaches a pivotal decision it cannot reasonably resolve, it hands the full context to a stronger advisor for a plan, a correction, or advice to stop—then resumes execution. You can adopt this division of labor manually even without the official Advisor tool.

Executor advances the task→Consult the advisor on plans, blockers, or finalization→ Continue with the advice→Finish with tests and acceptance checks

Good fit: long coding workflows, computer use, and multi-step research—many steps are mechanical, while a few architectural, risk, or directional decisions are pivotal.

Poor fit: one-step questions or tiny changes, and tasks in which every step genuinely requires frontier-level judgment. In the latter case, use the stronger model directly.

01 · Outcome before process

State the final deliverable, essential background, prohibitions, and acceptance criteria. Do not provide only “help me optimize this.”

02 · Match information to model capability

Give a strong model more of the objective and less of a prescribed path. Give a weaker model steps, examples, and a checklist.

03 · Require real verification

Have the model run the code, execute tests, inspect the diff, or confirm with a screenshot. Saying “done” does not make the work complete.

04 · Review at pivotal points

Review the plan before implementation, correct course when blocked, and inspect the result before delivery. An advisor need not join every step—only the high-leverage ones.

05 · Do not judge by model name alone

Tool permissions, context quality, reasoning effort, runtime environment, and acceptance method all materially affect the result.
