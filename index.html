环境自检

本站多数作品是重量级的实时 WebGL2 渲染，对显卡有真实要求。下面会实测一段与这些作品同量级的着色器负载， 并把结论逐条标注到每个作品上——它们之间的开销差了近百倍，笼统给一个结论没有意义。

在开始之前

这个对比在证明什么，不在证明什么

要证明的：需求描述的质量，会直接决定产出的质量。同一个模型，拿到一句话和拿到一份文档， 交出来的东西可能完全不在一个量级。

模糊需求：对于一些能力强的模型，即使需求很模糊，由于模型自身能力强，也可以很好的完成工作。 而对于能力稍弱的模型，则需要详细的描述任务过程、步骤等内容。

不能用来证明的：模型能力排序。那份《任务说明书》是 Claude Opus 5 (Ultra) 从它自己的实现反推整理出来的， 第 7 节还把 15 条实现陷阱全部列了出来。所以「文档组」本质上是命题作文 + 攻略—— 它们做的是同一道已知答案的题。拿它来排名模型强弱是不成立的。

另外：Claude Fable 5 (Max) 仍没有文档版。Claude Opus 5 (Ultra) 现在多了一次特殊的「自己出题自己做」： 它从自己的一句话标杆反推说明书后，再按这份说明书重新实现，因此已纳入同模型对照并以金色重点标记。 部分模型仍只有其中一组，站内已如实分开陈列。

思考档位说明：绝大多数作品使用当时平台提供的较高或最强可选档位。 模型名里的 Max / xHigh / Ultra / high 等后缀记录的是各平台实际选择的档位，不能跨平台直接等同（例如 GPT-5.5 只有 xHigh；DeepSeek 的 high 与 max 是同一档位的兼容写法；Ultra 还可能包含多智能体编排）。Claude Opus 4.8 是明确例外：一句话版为 (Max)，文档版为 (Ultra)。 因而下方是同模型系列的配对观察，不是 16 组算力完全一致的严格控变量实验。推理强度会以括号标记直接显示在模型名称中。

复测说明：有些模型之所以跑了很多次，是因为前几次结果与预期、宣传或其他评测呈现的水平严重不符； 但多次重跑后，结果依旧。

PS：这里只是测试了各个模型的 Coding 能力及模糊需求的理解能力。 对于其他如中文写作能力，不在此次测试范围内。

Codex 与 Claude Code 的 Ultra 并不是同一种模式，也不都等于最高单模型推理档位。Codex Ultra 可近似理解为 Max 级推理 + 自动任务委派；Claude Code Ultracode 则明确是 xhigh + dynamic workflows，而不是 Max。换言之，本页部分使用 Ultra 档位的样本——例如 Claude Opus 5——可能仍未用出该模型的最高单模型推理强度。

单价低，不等于把事情做完更便宜

有了任务说明书，就应该改用低级或便宜模型吗？恰恰相反：说明书能减少歧义，却不会抹平模型能力差距。把额度消耗、等待、失败、返工和人工复核一起算进去，低价模型的项目总成本反而可能更高。

规格书是能力的放大器，
不是能力的替代品。 真正该比较的，是每个「通过验收的结果」花了多少。

说明书抬高的是规格覆盖的下限，不会自动抬高执行质量的上限。

一、同模型配对显示了什么

在 16 组同模型配对中，V2 证据评分的覆盖部分从一句话组平均 40.58 / 59.5 上升到文档组平均 55.51 / 59.5。说明书确实让更多要求被写进产出。Claude Opus 4.8 是 (Max → Ultra) 的档位例外，因此这批配对不是统一严格控变量实验。

但执行质量——正确与稳定、视觉执行、交互完成度——分别是 30.19 / 40.5 与 31.26 / 40.5，没有显示稳定提升。这个样本支持“说明书改善指定功能覆盖”，不足以推出“说明书会让执行质量整体下降”，也不足以推出任何通用模型排名。

因此，跨组比较总分时，需求形式仍是重要混杂因素。要讨论说明书的影响，应优先看这 16 组配对结果，而不是把一句话组 30 件和文档组 23 件直接当成同构样本。

二、说明书做了什么，没做什么

说明书能减少“没想到”的失败：轨道根数、八颗卫星、哈雷彗星、离线约束和渲染管线写在纸上，模型更可能逐项实现。

它不能自动消灭“想到了但做错了”的失败。文档组仍出现环阴影混用坐标空间、金星半长轴写错、土星环缩放后实质消失、大红斑永远转不到可见面、太阳信息出现 NaN，以及渲染循环在后台持续倍增。这些问题往往不报错，只有打开作品、持续观察，再回到源码核对才能发现。

说明书降低了输入端的歧义，却没有替你完成输出端的验收。

V2 量表因此把“写了没有”拆成可追溯的功能、轨道模型、运行一致性和交互子项，并加入致命故障上限。但公式是自动的，不代表证据采集全自动：视觉与部分交互判断仍有人审成分。

三、这对成本判断意味着什么

站点原本的结论——“单价低不等于把事情做完更便宜”——仍然成立。更具体地说：

便宜的是 Token，贵的是确认它做对了。

同一份详细说明书下，站内记录的 DeepSeek V4 Flash 0731 (Max) #1 / DeepSeek V4 Pro (Max) 案例中，前者折算单位成本约低 77%，但 Token 消耗约为 15 倍、执行用时约为 5.3 倍、最终费用约为 3.4 倍。这是一组真实项目记录，不是标准化价格基准；它说明价差可能被等待、重试和复核吃掉，不足以说明所有同类任务都会如此。

真正该比较的是完成一次可验收结果的总成本：模型调用、规格准备、等待、失败重试、修 Bug、人工监督和最终复核。失败越静默，发现它的成本越高。

四、复测与证据边界

有些模型被多次运行，是因为早期结果与预期、宣传或其他评测呈现的水平明显不符；后续运行没有改变整体印象。但这些复测不是预先规划的，次数也不相等，因此不能用来估计所有模型共有的方差，更不能据此形成公平排名。只有 DeepSeek V4 Pro (Max) 的三次同条件一句话运行能直接说明本站观察到了同条件分差；MiniMax 与 Qwen 的跨度混合了需求形式、版本或环境。

这批样本还有四个明确边界：

  • 它只测试一种开放式 3D Coding 任务，不能代表写作、翻译、信息抽取或多数工程工作。
  • 平台、Agent 环境、缓存和计费口径并不完全相同，不是实验室控变量测试；Claude Opus 4.8 配对还存在 (Max → Ultra) 档位变化。
  • Claude Opus 5 (Ultra) 是说明书作者，也是随后按说明书作答的模型之一，存在“自拟题再作答”的优势。
  • 视觉和部分交互证据仍由人审，V2 证据评分提高了透明度，但没有消除判断误差。

因此，这批样本支持“详细说明书提高指定功能覆盖”，不足以形成通用模型强弱排序，也不足以断言说明书会降低执行质量。

五、四条可执行判断

  • 默认最强，但给降档设明确触发条件。不是因为最强永远最优，而是避免每次重做一张快速折旧的路由表。
  • 降档先看失败可见性。编译、测试或空结果会立即暴露，更适合降档；轨道、视觉和长期循环这类静默错误，需要把人工发现成本算进去。
  • 先写验收，再选模型。没有可执行检查，多模型试跑容易只比较表面观感。
  • 顾问策略只用于卡点可识别的流程。执行模型不会为自己没有意识到的错误主动求助。

不要为了省 Token，去换一次需要人来发现的失败。

不默认最强，也不默认最便宜；先按风险判断，再用实测结果路由。

真正应该优化的是：

完成一次可验收结果的期望总成本。

它不只是模型账单，还包括模型调用与 Token 消耗、规格准备、人工盯守、最终复核、失败重试、修 Bug、等待和延期。

更稳妥的策略是：

  • 未知、复杂、开放式或失败昂贵：优先让最强的适用模型直接完成，避免把价差变成返工。
  • 清晰、低风险、机器可验收、需要批量执行：使用经过同类任务验证、能够稳定通过验收的最低成本模型。
  • 流程长但多数步骤机械：可以实测“较小模型执行 + 顶级模型顾问”，但必须与顶级模型独立完成作对照；结果取决于任务，应在自己的工作负载上评估。
  • 暂时没有可靠数据：先建立质量基线、验收标准和测试集，再验证是否值得降档。

这些判断有明确边界：样本只覆盖一种开放式 3D Coding 任务；平台、Agent 环境和计费口径不完全一致；Claude Opus 4.8 配对存在 (Max → Ultra) 档位变化；Claude Opus 5 (Ultra) 既写说明书又按说明书作答；视觉和部分交互证据仍依赖人审。有些模型因早期结果与预期、宣传或其他评测不符而被复测，后续结果没有改变整体印象，但复测次数不等、也非预先设计，不能估计共同方差或形成公平排名。

这些词描述的是模型如何思考、调用工具和组织工作，不等同于模型能力排名。不同平台的名称并不统一，以下定义只用于解释本站语境。

ADVISOR STRATEGY

顾问策略

较快、较便宜的执行模型负责端到端推进任务；当它遇到无法合理解决的关键决策时，才把共享上下文交给更强的顾问模型。顾问返回计划、纠偏或停止建议，执行模型随后继续工作。

执行模型推进→关键决策时咨询强模型→执行模型继续交付

它不是 sub-agent 编排：顾问不调用工具、不直接交付结果，也不会把任务拆成一组 worker；它只向执行模型提供建议。

ULTRA REASONING

Ultra 推理档位

本站用 Ultra 表示测试平台为某个模型提供的最高或最强 Agent 推理档位。它不是跨厂商统一标准，也不一定是模型正式名称；其他平台可能把类似档位称为 Max、xHigh、high 或 thinking。

意味着什么：主 Agent 通常拥有更大的推理与工作预算，可以投入更多规划、检索、自检和验证；代价可能是更长的运行时间与更多额度消耗。Ultra 仍不等于“保证正确”。

本站语境下的建议：在支持 sub-agent 的环境中，优先让主 Agent 使用 Ultra 档位，由它判断是否拆分任务、分配合适的 sub-agent，并负责最后的整合与验收。

RECOMMENDED ORCHESTRATION

Ultra 主 Agent 如何组织 sub-agent

主 Agent 保留目标、上下文和最终责任；sub-agent 只接手边界清楚、可以独立完成的部分。

主 Agent · Ultra理解目标与验收标准→ 判断是否拆分识别可独立或并行的子任务→ 分配 sub-agent按专业、速度与成本选择执行者→ 汇总与验收复核结果、运行测试并统一交付

与顾问策略的区别：sub-agent 会实际完成一个子任务并返回结果；顾问模型只给建议，原执行模型仍从头到尾掌握主流程。

AGENT

Agent

能够围绕目标自主读取上下文、调用工具、修改文件、运行验证并持续推进的主执行者，不只是回答一轮问题的聊天模型。

SUB-AGENT

sub-agent

由主 Agent 委派的子执行者，负责一个具体、边界明确的任务。它可以并行调查或实现，但结果仍应由主 Agent 汇总和复核。

REASONING TIER

推理档位

同一模型可使用的思考与工作预算设置。更高档位通常更愿意规划、检查和处理长链路任务，但也可能更慢、消耗更多额度。

COST TO ACCEPTANCE

验收总成本

得到一次可接受结果所需的全部成本：模型消耗、等待、失败重试、修 Bug、人工监督与最终复核，而不只是单次 Token 单价。

SCORE ≠ TIER

证据评分与主观梯队

证据值来自源码审计、一致实跑和人工视觉审查，公式与排序自动执行；梯队是站点作者对实际完成度的主观归类。
